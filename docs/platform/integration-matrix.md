# Platform integration matrix

Which shared service is connected to which part of the platform, and how far each connection has been proven. A test (`tests/test_platform_matrix.py`) checks this file against the code: every "Connected" row must name a real file and function and real automated tests, every file in the project that talks to the outside world or to Claude must be accounted for here, and every live-testing claim must say "Not live-tested" with its reason. Adding a module without adding it here fails that test.

## How to read the columns

- **Status.** *Connected*: the module asks the shared service through its common interface, under the owner's central controls. *Not applicable*: the service has no use in that area. *Not connected*: relevant, but not connected, with the exact reason.
- **Implemented / Connected / Automated tests / Live.** A *Connected* row is implemented in code and connected to its module by definition. "Automated tests" lists tests that exercise the connection. **No connection has been live-tested**: that needs a real provider account, a browser logged in to a real account, or an authorised GitHub Actions run, and none of those exist in the isolated working copy (Actions are on hold by your instruction). Each live column says which.
- Every service is controlled centrally in `observatory.yaml` under `services:` (and by the Controls tab or `observatory controls`), with optional purpose-specific and host-specific overrides. Initial defaults turn every supported capability on (see capability-matrix.md), keep each module's old behaviour as the fallback, and let the owner turn anything off.
