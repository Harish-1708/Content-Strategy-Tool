# Batch 2, stage 1: the external skills connection and the two registries (Update 70)

What this stage does, in plain terms. Later stages (the foundation chain, the brief pipeline and the rest) are built on it and are not in this update yet.

## 1. The Aaron marketing skills, connected externally

- **The whole repository is checked out at a pinned commit**, scripts and references included, because the auditors return NOT_SCORED without their runtime files. Nothing is copied or rebuilt: a copy goes stale the moment the repository changes.
- **The pin** is `repo.pinned_commit` in `external_skills.yaml` (now `7932adf517`, the commit of 2026-11-16). Change it by hand, only after reading the update report.
- **Skill text is data.** It is read, hashed, size-capped (60,000 characters; the largest skill is 26,179) and wrapped so the model treats it as a published method to apply to the brand's own inputs, never as an instruction to the tool. No script of the repository is run by this stage. A skill path can never reach outside the checkout (symlinks included).
- **All 120 are reachable.** `external_skills.yaml` records each skill's verdict from the research report (64 useful, 35 conditional, 21 not useful) and two things the tool acts on:
  - `state: waiting_for_access` (15 skills, re-judged row by row in Update 70; each says what it `needs:`): audience-segment-builder, campaign-architect, search-term-miner, attribution-reconciler, fatigue-frequency-manager, paid-measurement-loop, list-segment-builder, performance-analyzer, roi-calculator, launch-retro-analyzer, offsite-signal-analyzer, performance-monitor, rank-tracker, dark-social-attributor, social-measurement-loop. They are built ready, paused until the stores' own numbers exist (GA4, Search Console, customer or platform exports, measured results), and say `NEEDS_INPUT` with the reason. Asking for one by name does not unlock it. They are not removed. (ad-test-designer designs tests from a brief and needs none of them: ready.)
  - `auto_run: false` (the 21 not useful). Reachable when asked for by name, never started by a schedule or a chain. cold-outbound-sequencer carries `routes_to:` the separate email outreach tool and never starts here.
- **The lock is real.** `read_skill` asks the policy first (`may_start`): a waiting skill, one routed elsewhere, or one that never auto-runs (unless asked for by name) is refused with the reason, so no caller can read its text around the lock. `skills --action read --skill <path>` is the one door; the foundation chain will use it.
- **verify** also fails on edited skill text (an uncommitted change) and on a checkout whose origin is not the pinned repository (a fork with the same commit).
- **Actions > Skills and registries** (`skills.yml`): `status`, `verify` (fails when the connection cannot be trusted: not the pinned commit, a skill or runtime file missing), `update-report` (what changed upstream since the pin; nothing is adopted), `catalogue` (writes `data/_shared/skills_catalogue.json`, each skill's hash; git keeps the history).

## 2. The two registries (approved design: Sheets tabs + the git log)

- **Per brand, an append-only event log** `data/<brand>/registry/events.ndjson`, committed with the rest of `data/`. Nothing rewrites or deletes a line; a damaged line is counted and skipped.
- **The narrative canon.** A skill's output is only ever *proposed*. Nothing is canonical until the OWNER approves it (the Decision column of the Canon tab); a newly approved text for a section supersedes the earlier one. The tool cannot approve.
- **The offer-claims ledger.** Each claim is verified, unverified, blocked or conflicted. Only the owner can mark a claim verified. `gate` checks a piece of text against the ledger, sentence by sentence, but only sentences that say something checkable (an award, press, a ranking, a health claim, a figure, a customer count). BLOCKED: it repeats a claim the ledger blocks or marks conflicted, by the claim's distinctive words or by its text and reason, short forms written out (GMA = Good Morning America). NEEDS_REVIEW: it matches an unverified claim, denies something (a denial is not repeating it), or nothing verified and no approved canon covers it. OK: nothing checkable, or the owner verified a claim it is about, or approved canon says it. Its settings (threshold, short forms, negations, wording lists) are in `claims_gate.yaml`.
- **The replay is strict.** An event that is not the owner's decision or verification, or a decision on something that is not a proposal, is ignored and counted (a person with file access cannot approve canon by editing the log). Proposal ids never repeat, a timestamp must be UTC, and two claims with the same words in a different order are different claims. `canon --action history` lists the git commits that touched a brand's registry.
- **Seeded from the story bank's own gaps.** `brands/<slug>/claims_seed.yaml` holds 12 (Swoveralls), 10 (DudeRobe) and 13 (DeFi Snacks) claims copied from each brand's "Gaps / not found" section as blocked, unverified or conflicted, never verified. Each brand also has its part of the story bank (`story_bank_material.md`, with the two corrections: DudeRobe is a separate company from DUDE Products / Dude Wipes; Swoveralls' founder is Kyle Bergman) ready for the foundation chain. Seeding twice adds nothing.
- **Sheets.** Once a brand has registry events, its sheet gets a Canon tab and a Claims tab (the tool owns the other columns; Decision and Notes are the owner's and are never overwritten). The sync reads the Decision column before it rewrites the tabs.

## What is not proven

- The workflow's checkout and the real Canon and Claims tabs have not run live (the connection itself was run against the real repository in the sandbox).
- The gate is lexical (words, not meaning). It is a safety net, not a fact-checker: a claim phrased very differently from the ledger's wording can reach NEEDS_REVIEW instead of BLOCKED, and a checkable sentence that the owner has verified (or approved as canon) is OK by design. A sentence with no checkable pattern is never examined.
- "Only the owner" is a rule about who may change a status in the tool; the sheet cannot tell who typed a Decision, so whoever can edit the sheet can decide. Keep the sheet's edit access to the owner.
- A customer's medical condition is never kept in the story bank (the Swoveralls review that disclosed one was removed).

## Stage 2: the story-bank refresh and the foundation chain

**The refresh** (`Actions > Skills and registries > refresh-story-bank`, also automatically on the 2nd of every month; run it before each brief cycle too). Per brand it searches (the brand's standing questions, then one search per Gap on its watchlist), reads the public pages, and asks the routed AI client to pull out checkable facts, each with the EXACT sentence it rests on. Then:
- the code checks the quotation really is in the page it fetched (a model is never trusted for that), that the fact or quotation names the brand, and a reviewer that reads only the fact and the quotation must confirm it. No source, a quotation not in the page, or no confirmation: the fact does not go in, and the run names why;
- a new fact enters ONLY as an **unverified** claim, with its source address, the date it was read and the quotation. Nothing is verified and nothing becomes canon: only you do that, in the Claims tab;
- a fact about something the ledger already has, but with different numbers, is added as **conflicted** and linked to the old claim. Both stay for you to decide; a verified claim is never touched;
- old facts are protected: the registry is append-only, so the refresh cannot delete or change anything, and it has no way to write your Decision and Notes columns. A page is read once (it is remembered).

**The foundation chain** (`foundation`): nine skills applied in order to one brand's own material (positioning, audience beliefs, category narrative, strategic narrative, message house, message system, language, story bank, proof points). Each step reads its skill through the lock (a waiting skill is refused with NEEDS_INPUT), gets only the brand's facts, its story bank, the claims ledger with what NOT to state and the canon you have approved, and must list what it lacks instead of inventing it. Its text goes through the claims gate: a text that repeats a blocked claim is sent back once and then refused (recorded, never proposed); checkable statements nothing verifies are proposed WITH that note. Every result is a **proposal** in the Canon tab. `max_steps` (default 3 per run) keeps the AI calls inside the caps; the next run continues. The log of each registry now carries an integrity chain (each line holds the hash of the line before): `canon --action status` warns when a line was edited, shortened or reordered.

## Stage 2, round 3: what the first real runs showed, and what changed

- **Conflicts mean the same fact stated differently, or two statements that cannot both be true.** The first real refresh called 12 facts "conflicts" because both sides held a number (a rating against a return window). The detector now finds claims about the same THING (shared content words, or the distinctive words of a claim's name; a figure is also compared with other figures of the same kind), and a reviewer must say the two statements cannot both be true. Two facts that merely both contain numbers are not a conflict. A real conflict is linked to EVERY claim it contradicts; the old claims are never touched. Without a reviewer nothing is called a conflict.
- **Where conflicts live:** in the **Claims** tab, with status `conflicted`; its `reason` names the claim(s) it cannot agree with. There is no separate Conflicts tab. `canon --action reclassify-conflicts` (Actions > Skills and registries) re-checks the conflicts the refresh created: a pair that is not really a disagreement goes back to UNVERIFIED with the reason written down (the link stays in the log, nothing is deleted, and a claim you decided is never touched).
- **A failed model call is diagnosable.** A foundation step whose model call fails is asked once more (a rate limit or a brief outage is usually over in seconds); if it fails again the run prints the error's own words (a key is never printed), how many tries were made and which route the routed client reports having tried. The same cause is printed for a failed extraction or review in the refresh. `max_calls` limits the model calls of a run (a retry or a correction counts); `max_steps` limits the steps.
- **The Canon tab shows the gate note** (a Gate note column: what the gate found and what the proposal still needs), and the structured needs and the claims the model said it relied on are stored with the proposal; a claim it names that it was not given is flagged in the note.
- **The refresh:** every dropped fact is printed (up to 20, then "and N more") so the count and the lines agree; a refresh in which nothing could be read and reviewed exits with an error and the causes; after the new-entry limit no more pages are fetched or reviewed (no more AI calls), and the unfinished page is read again next time; a page is remembered as soon as it was handled; LinkedIn, Threads, Bluesky, Snapchat, Discord, WhatsApp, Telegram, Tumblr and Mastodon are not sources; the quotation is stored whole; `--max-new` sets the limit.
- **The foundation chain:** a misspelt step name is refused (exit 2) with the list of sections; a brand with no material is refused rather than invented for; the chain checks the skills connection itself; `--redo` replaces the tool's own earlier UNAPPROVED proposal (an approved text only changes by your approval); cut inputs are named in the note.
- **The registry log** now starts its chain with a fixed first value, so deleting the first line is caught, and an older log is SEALED with a digest of everything it already holds the first time the tool writes to it, so an edit in the old part is caught too. `canon --action status` names the problem.
- **Before each brief:** the brief workflow refreshes the story bank first (a checkbox, on by default); a failure of the refresh never stops the brief.
- **The Apify voice lane** has a spending cap per run (the sum of its calls' ceilings, default 3 dollars, `CONTENTINTEL_VOICE_APIFY_RUN_USD`): many small calls can no longer add up past it.

## Stage 2, round 4: the free pool first, fewer bigger calls

- **The refresh and the foundation chain now ask the free pool first.** Until now their purpose (`foundation`) was not in the AI Gateway's routes, so every call went straight to Claude (this was a mistake in the earlier notes, which said the pool came first; the first foundation failure on an empty Anthropic balance proved it). `foundation` is now a purpose in `observatory.yaml` (`services.ai_gateway.use_for` and `routes`, both `gateway_first`): the pool answers when it can and Claude is only the fallback, so a refresh or a chain no longer depends on the Anthropic balance alone. The route is the same for the refresh and the chain (one purpose, `foundation`). To send it to Claude only, set `services.ai_gateway.routes.foundation: claude` in the Controls tab. When the pool has no answer the call goes to Claude and the failure message names the route it tried (`route tried: gateway, claude`). Honest limits: the free models write less well than Claude, and the refresh's reviewer is then the same pool as its extractor; the gate, the quotation check and the owner's approval still stand, and nothing the pool writes is canonical until you approve it.
- **Fewer, bigger calls.** The reviewer that decides whether two statements contradict now gets every pair of a page together, 20 pairs per call, instead of one call per pair; `reclassify-conflicts` does the same (12 conflicts are one call). A pair the answer leaves out, or a call that fails, falls back safely (the refresh: no conflict; the re-check: it stays a conflict for the owner). `--max-calls` counts calls, so a limit of 6 means at most 6 (the re-check no longer overshoots it). The refresh has its own limit of 48 calls per run (`--max-calls` changes it): when it is reached no more pages are read and the rest is left for the next refresh. Duplicates still do not count toward the new-entry limit, because they add nothing; the call limit is what bounds the spend.
- **The foundation prompt has three sections, on purpose:** DO NOT STATE (the ledger blocks or disputes these), UNCONFIRMED (not verified: the model must never state them as fact; if one is useful it writes it as unconfirmed and lists it in `needs_input`) and MAY STATE (verified by you). Before round 3 unverified claims sat under DO NOT STATE while the gate only asked for review on them; the prompt and the gate now agree. The gate still flags any checkable statement nothing verifies, and every result is a proposal.
- **Keys and tokens are hidden in error messages even when short** (anything after `key=`, `token:`, `Bearer`, `secret`, `password`, or shaped like `sk-...`).
- **The Save step keeps `always()` on purpose:** the registry is append-only, so a failed foundation run that proposed some sections still keeps those (they cost AI calls); a failed run can never overwrite good data, only add to it. It stages only `data/_shared/skills_catalogue.json` and `data/*/registry`.
- **One ranked list per job.** The refresh's extraction, its review, the conflict check and each foundation section now each ask their own lane (`story_extract_json`, `story_review_json`, `conflict_check_json`, `foundation_json`) instead of one shared general lane, so the pool retest can rank providers for each exact job. The lists are seeded, not yet measured: see `docs/ai/ranked-lanes.md`.
